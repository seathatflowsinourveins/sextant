# Starting clean

A dedicated WSL distro with none of the old campaign's rules, hooks or tabs, loaded from GitHub (owner, 2026-11-06).

## What the owner does once
In PowerShell on Windows. It can't be started from the old WSL, because Windows access is off there.

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.cloud-init" | Out-Null; Copy-Item "\\wsl.localhost\northstar\home\choreo\Developer\sextant\deploy\wsl\sextant.user-data" "$env:USERPROFILE\.cloud-init\sextant.user-data"; wsl --install Ubuntu-26.04 --name sextant --location Z:\WSL\sextant --vhd-size 200GB --no-launch; wsl -d sextant --user root --exec cloud-init status --wait; wsl --terminate sextant; wsl -d sextant
```

Then follow the new distro's first login: sign in to GitHub, add the Orca server in your Orca app when it shows the link (`Settings > Remote Orca Servers > Add Server`, see **Pairing Orca** below), and sign in to Claude and Codex. dsh asks for its key the first time it starts. Nothing else is typed. On another machine, copy `deploy/wsl/sextant.user-data` to that `.cloud-init` folder from a clone of this repo.

## What happens
1. `wsl --install` creates the distro without opening it, and cloud-init reads the user-data file named after it ([Ubuntu's guide](https://documentation.ubuntu.com/wsl/stable/howto/cloud-init/), read 2026-11-06). It creates the user and installs the GitHub CLI, Docker Engine for rootless use, and Orca. The restart is what makes `/etc/wsl.conf` take effect, as on the old host.
2. The first login signs in to GitHub, clones this repo, and runs `deploy/wsl/setup.sh`.
3. `setup.sh` installs uv, Node, just, Claude Code, Codex and dsh at this repo's pins, then rootless Docker, `devc`, gitleaks, the native dsh-tui profile and local research retrieval (below). It pairs Orca's headless server on its own port, 6771, by Orca's pairing flow, then runs it as Orca's own per-user service (`orca serve service install`, with this repo's terminal limits as a drop-in). It adds this project, installs the Claude shelf `.claude/settings.json` declares (`just shelf`), adds a Claude lead in a tab, and runs `just accept`. This machine's `.wslconfig` has `guiApplications=false`, so Orca opens no window here: your Orca app connects to the server.
4. The lead's first steps: read the owner's research package, from this repo's release `seed-research-2026-10-09` or the Windows Desktop, as a start point only; then `docs/design.md`'s build order.

**Pairing Orca.** If your Orca app runs on this Windows PC, give `127.0.0.1` as the address: Windows reaches WSL on localhost with no firewall rule. The app then says the link points back to this device; tick **I reach this address through an SSH tunnel**, because WSL's localhost is the tunnel here. The tick only permits a loopback link: Orca still contacts the server and checks its key before saving it ([its pairing check](https://github.com/stablyai/orca/blob/a162e08b29b2883b02d8a0dfcc99e26c80b2cfe7/src/main/ipc/runtime-environments/runtime-environment-pairing-verification.ts#L52-L106)). From another computer, Windows' Hyper-V firewall blocks the port unless a rule admits it, as the old host's runbook does for 6768 (`northstar@b384d298d217:docs/handoff/workstation/phase-0-legacy.md`, section 7a). Run this once in an Administrator PowerShell, then accept the suggested tailnet address:

```powershell
New-NetFirewallHyperVRule -Name 'Sextant-Orca-6771' -DisplayName 'Sextant Orca TCP 6771' -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol TCP -LocalPorts 6771
```

**Staying clean.** Setup runs `just lifecycle` once.
- **git's own upkeep:** `fetch.prune` drops branches GitHub deleted at merge, and `git maintenance start` puts this repo on git's scheduled upkeep.
- **A daily Orca automation:** the `Lifecycle sweep` runs in this checkout, never in a worktree of its own ([Orca's automations](https://github.com/stablyai/orca/blob/a162e08b29b2883b02d8a0dfcc99e26c80b2cfe7/docs/site/content/docs/cli/automations.mdx)). Its precheck skips the run when there's nothing to do.
- **What the sweep does:** it removes worktrees whose PRs merged, along with their branches. It deletes only branches that are merged, and keeps the rest with a note on issue #35. When a newer Orca release has been out three days, it opens a PR moving the pin.

**AO, for a lane PR's fix-CI and review loop.** Orca dispatches the lanes, and AO only works a PR its lane worker has handed off ([evidence](research/2026-11-06-agent-orchestrator.md)). `just ao install` installs it at the pin, and `just ao project` gives it its own clone. In the main checkout's `AO daemon` tab, `just ao daemon` runs it on port 3301, since another distro holds AO's default port. After a worker's `worker_done`, `just ao claim <PR>` gives that PR to one AO Codex session, which never merges. `ao session ls` shows the loop.

**The Sextant GitHub App, for AO's and the lanes' own rate budget.** The owner's login and every PAT share one 5,000/h REST budget; an App installation has its own. `just gh-app install` installs the pinned `@octokit/auth-app`. Once `SEXTANT_GITHUB_APP_KEY_B64` is in the store, `just gh-app ids` records the installation ID. Then the `AO daemon` tab runs `just gh-app daemon` instead of `just ao daemon`, which restarts AO on a new one-hour token before each expires, and a lane tab starts its agent with `just gh-app tab -- <agent>`. Its `gh` gets a fresh token on every call. The lead and the owner keep the owner's own login. The token is never printed or written; `just gh-app run -- gh api rate_limit` shows the App's own `core` budget.

**Updating Orca.** The app's *Update Orca on the server host* can't update this server, because Orca leaves a `.deb` install to its host ([its updater](https://github.com/stablyai/orca/blob/a162e08b29b2883b02d8a0dfcc99e26c80b2cfe7/src/main/updater/lifecycle/updater-remote-status.ts#L33-L45)). A PR moves the pin in `deploy/wsl/sextant.user-data`; then `just orca-update` in the distro installs that package and reinstalls Orca's service, which restarts the server. Tabs keep running, since the terminal host outlives a server restart ([Orca's docs](https://github.com/stablyai/orca/blob/a162e08b29b2883b02d8a0dfcc99e26c80b2cfe7/docs/site/content/docs/remote-servers.mdx#L187)).

If a step stops, the window says so and waits. A session outside the distro can read what happened in `/mnt/wsl/sextant/first-login.log`, which never holds the pairing link or a sign-in, and fix it on GitHub. You press Enter to pull the fix and try again, and you don't type a command.

## What it is and is not
- **Clean:** the distro has its own home, so no old `~/.claude` rules or hooks load. Its Orca server lists only this project. Your Orca app shows it as a separate server, and can remove the old ones whenever you like.
- **Settings:** New York time, not the Windows clock; systemd on; services outlive a logout; Ubuntu's metrics off, so it asks nothing at first login. `.wslconfig` is shared by every distro and already tuned, so this leaves it alone. `just accept` proves each of these in the distro.
- **Windows access stays on,** so the lead can read the Desktop and open a folder for the owner by its full path (`/mnt/c/Windows/explorer.exe`), without asking. Windows programs are off `PATH`, so none shadows a Linux tool.
- **What that exposes:** a tab could also reach every distro's disk on `Z:` or run `wsl.exe --shutdown`, which would stop the old paper nodes. `AGENTS.md` forbids both, as a rule rather than a wall. `[interop] enabled=false` in `/etc/wsl.conf` and a restart make it a wall, at the cost of opening nothing on Windows and clicking each sign-in link by hand.
- **Shared with the old lanes until they retire:** RAM, and one WSL network namespace, so a tab here can reach loopback ports on the old distro. `AGENTS.md` allows reading them, never writing (owner, 2026-11-06). `/mnt/wsl` mounts are visible too. Those folders belong to uid 1000, the old lanes' user, so this distro's user is uid 1500 and can't write to them.
- **Outside the container:** native Orca tabs have neither its firewall nor its read-only binds. That is the owner's call for this distro, which holds nothing else: "QUALITT AND SOTANESS ITSELF RATHER THAN SECURITY OVEREGINNERING". Unattended agents still run through `devc`.
- **The debug port:** TradingView Desktop's `127.0.0.1:29222` is reachable from this distro, unauthenticated, with brokers connected. The owner accepted that on the condition that agents never connect to it (`docs/adr/0021-tradingview-display.md`), so that is a rule in `AGENTS.md`, not a wall.
- **Not here yet:** WeKnora is a named hold, with no service or credential provisioned.
- **Nothing here waits on a prompt** (owner, 2026-11-06: "can you launch the login bypasspremiss so your future workflow will not be gated"). Orca launches every agent with its bypass flag by default ([its docs](https://github.com/stablyai/orca/blob/a162e08b29b2883b02d8a0dfcc99e26c80b2cfe7/docs/site/content/docs/agents/supported.mdx)), `setup.sh` answers Claude's own dialog up front, the GitHub login carries the `workflow` and `user` scopes, and the user has passwordless sudo. Root can also write the old lanes' folders, which is why `AGENTS.md` forbids that as a rule.
- **Docker is rootless only:** all distros share one network namespace, and the old host's rule is one rootful daemon on it (`docs/decisions/0074-host-baseline.md`). Cloud-init masks the system `docker` and `containerd` units before installing the packages, so no rootful daemon starts here, and setup runs Docker's `dockerd-rootless-setuptool.sh install` as the user ([Docker's rootless mode](https://docs.docker.com/engine/security/rootless/), read 2026-11-06). Its network lives in rootlesskit's own namespace; only published loopback ports reach the shared one.
- **Size:** 200 GB at most, so it can never outgrow `Z:`'s free room, the old host's capacity rule. Its lead saw this and has no objection, and asks to start it after g2's install groups have applied, or with a word first, because all distros share memory.
- **On `Z:`:** a `Z:` reset takes this distro with it unless the owner names it as kept. Nothing is lost that isn't on GitHub, except sign-ins, which the owner redoes.
- **One writer:** the new lanes start on research and sim. A paper account moves only in a handover the owner confirms, with its old writer stopped first.

## Native dsh and research retrieval

Orca's dsh agent launches `dsh-tui .`. dsh-tui 0.19.0 runs on the sandbox's own dsh 0.2.2-rc.1, from `.devcontainer/agents`. Its profile, `~/.dsh/profiles/dsh-tui`, receives Context7, Exa, DeepWiki's documentary tools, paper-search, Brooks review, reference-checker, session-search and billion-context through native bundles and ordered patches, and carries the two packages Orca's dsh hooks load. This profile is for synthesis; blind legs use an unenhanced profile and an empty separate `DSH_HOME`.

dsh asks for its DeepSeek key the first time it starts, in its own guide; that is the owner's sign-in. An agent starts it with the stored keys instead: `scripts/with-keys.sh --strict -k DEEPSEEK_API_KEY -k EXA_API_KEY -k CONTEXT7_API_KEY -- dsh-tui .`. The TUI's pi-ai OAuth row is disabled. Missing upstream MCP connections remain visible failures, not proof of an active inventory.

OpenViking runs on `127.0.0.1:21933`, backed by a separate rootless embedding container on `127.0.0.1:21934`. Billion-context's user port is `21935`, with its dsh lane zone starting at `21936`; Orca's unit drop-in carries the same settings, because the old lanes already listen on upstream's defaults, `1933`, `1934` and `18787`. Without those two settings billion-context does not load at all (`config/dsh/bili-ports.cordis.yml`). No old service is reused.

Run `just index` to import a fresh copy of the committed `docs/` tree, under a URI containing its git revision. Retrieval is an explicit synthesis opt-in: `dsh-tui --patch config/dsh/openviking.cordis.yml .`. Use `find`, then read the returned `viking://` URI for citations. The MCP exposes write/admin tools: this disposable index is not a read-only boundary or canonical memory. Re-import a fresh repo copy into a fresh service workspace if changed. There is no automatic conversation capture, memory commit or external URL ingestion. See [the operational lesson](handbook/retrieval.md).

**The receipt** ([the design](design.md), line 126): add `--patch config/dsh/startup-receipt.cordis.yml` beside OpenViking's, wait for the composer, then `node scripts/dsh-native-acceptance.mjs --run --tui <log>` with the log it wrote under `~/.northstar/native-state/dsh/logs/` (the harvested diagnostic keeps its upstream path). Exit 0 means `warnings: []`, `forbiddenActive: 0`, Orca's hooks attached and every selected provider active. Orca attaches its dsh hooks when its server starts, so after the first install run `just orca-update` once.

The hook is `.githooks/pre-commit`; setup selects it with `git config core.hooksPath .githooks` and installs the Dockerfile's exact gitleaks/actionlint releases with its checksums. `systemctl --user status sextant-openviking docker` shows the research service and the rootless daemon; the model and index are disposable files under `~/.local/share/sextant-openviking/`.
