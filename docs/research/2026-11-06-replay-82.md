### Population, clock and label

- Session: the US/Eastern calendar date of a bar's `ts_event`; sessions are `2026-10-26..29`. Extended-hours bars are in the population because the receipt records them; no RTH-only filter is claimed.
- Signal clock: a signal at bar `t` uses only completed bars with `ts_event <= t.ts_event`. The bar's own OHLCV is complete at its `ts_event`; no later bar may enter any signal.
- Label: the realized net return of the native round trip the arm actually executes. There is no forward-label model, no cross-validation fold and no holdout here; the screening table orders arms by that realized, after-cost, per-trade return.
- Eligible population per arm is the set of signal bars where the factor's inputs are computable; the count is reported. Non-computable bars are excluded and shown, never zero-filled.

### Execution, cost and latency convention (frozen)

- Native path: `natilus_trader.backtest.BacktestEngine` 2.0.0rc8, the same engine `BacktestNode` wraps, fed by `ParquetDataCatalog` from the verified catalog. Venue `ALPACA`, `NETTING`, `CASH`, starting balance `1,000,000 USD`, `bar_execution=True`, `L1_MBP`, default fill model (`prob_fill_on_limit=1.0`, `prob_slippage=0.0`), `StaticLatencyModel()`.
- **Documented deviation:** the catalog's bar volume is stamped at precision 1 while each Equity's `size_precision` is 0; rc8's matching engine silently drops precision-mismatched bars (nautechsystems/nautilus_trader#5461), so a `BacktestNode` run fills nothing. The screen keeps the catalog bytes unchanged and re-stamps only the volume quantum at the instrument's integer precision (values unchanged, asserted integral) before `add_data`. This is a data-loading adapter, not a different simulator; it is recorded here before results.
- Entry/exit: a market order submitted in `on_bar` at the signal bar settles at that bar's close (rc8 bar-execution contract, zero latency). Exit at the close of the bar `H = 30` one-minute bars later; if that bar is missing or past the session's last bar, exit at the session's last bar. No position crosses a session boundary.
- Size: exactly 1 share per entry, one position per symbol at a time, no re-entry while open and
  none at the exit bar's close (a one-bar cooldown keeps every planned action executable under
  bar-close settlement), no compounding and no sizing claim.
- Costs: `MakerTakerFeeModel(maker_rate=0, taker_rate=cost)`; market orders are TAKER. 1x = **3 bps per side** — the documented *assumed* convention, not a measured calibration (`docs/research/2026-11-06-exit-econ-98.md:3`; `2026-11-06-exit-grid-141.md:97`; ADR-0025:54). 2x = 6 bps per side, the `cost_stress_multiple = 2` stress (ADR-0003, ADR-0018). No spread, borrow or market-impact model exists for bars.
- Zero latency, bar OHLC paths and 1-share sizing all understate real execution; the table is a screening order only.

### Corrections before the reported run

The protocol above was frozen before any selection. Three implementation defects were found while
executing it; each is recorded here because it changes how the frozen plan is executed, not what is
estimated:

- The not-ready arms first logged an empty return series against non-empty `days`, which the canonical
  `TrialLog` refuses. They now log no session days at all; no return is imputed.
- Plan actions were dispatched once per subscribed bar (up to 54 per minute) instead of once on the
  instrument's own bar, which inflated round trips. Each action now executes only on its own
  instrument's bar.
- The plan could re-enter at the exact exit bar's close. Bar-close settlement cannot order an exit and
  a re-entry inside one bar, so the plan now keeps a one-bar cooldown after each exit.
- The `hold_flat` arm was renamed `buy_and_hold` on the lead's follow-up before this report: it is a
  buy-and-hold benchmark that takes a position, not a control; `cash` is the only zero control. The
  pre-rename run is superseded and the reported ledger rows carry the new name.
- Session P&L is now read from the engine's own Money, not accumulated from fill arithmetic: the
  strategy samples `Portfolio.realized_pnls(venue, target_currency=USD)` on each `PositionClosed`
  event and records the difference from the previous sample, so a session's return is that session's
  native realized P&L, not the account's running total. The boundary is the portfolio Money, not
  `PositionClosed.realized_pnl` alone: a 10.0000 to 10.0049 round trip at 3 bps closes with the
  position event's unrounded 0.0049 USD while the portfolio reports Money(0.00, USD), and the P1
  witness compares the ledger return to that portfolio Money. The metrics keep Decimal equity until
  the return-schema boundary. Upstream at the pin
  (NautilusTrader 2.0.0rc8 `d53849b`) is `crates/portfolio/src/portfolio.rs:583`, whose
  `realized_pnls` returns `Option<IndexMap<Currency, Money>>`; the generated Python stub is
  `python/nautilus_trader/portfolio/__init__.pyi:60`. A 10.0000 to 10.0049 round trip at 3 bps
  therefore reports the native USD Money (`0.00`), not the 4.9e-9 fill difference.
- `INSUFFICIENT_N` factor rows are shown unranked. Ranking a row the study itself calls insufficient
  is what the review lens forbade; only rows with a sufficient sample consume a rank, and the table
  says so in its cost note.

Two screening runs made before these corrections were discarded rather than reported; they are not the
table that follows. The estimand, arms, population, cost convention and ordering criterion are
unchanged. The reported run must show planned entries and native round trips matching per arm before
its table is used.
